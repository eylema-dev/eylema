# Embedded human oversight — G11

G11 revision4 extends the accepted [G10 executor](deterministic-runtime.md) in owned safe Rust. This is an embedded native API, not a deployed person-login service, HTTP endpoint or browser approval screen. Runtime production still depends only on owned contracts; its native development consumer uses owned platform services. Cargo inventory, selected portable libraries, guards and workflow are unchanged.

## Trusted person verification and accepted requirements

Only the HostKey returned by this Runtime can enroll_verified_human. The embedding host must independently verify the person and determine scoped permissions before invoking this method. HumanSession is opaque, bound to that runtime/enrollment slot and not serializable. Ordinary Session, claimed principal/human fields, checkpoint/governance references and model output cannot mint it. ApproveAction, RequestCancellation and GovernPolicy remain distinct scoped permissions; verified humanity alone grants none. The test host attestation is explicitly simulated; actual person authentication is not_run and belongs to the later host/browser integration.

create_governed_task requires HostKey and installs immutable accepted oversight independently of task-request declarations. At admission and each step, the runtime composes these accepted checkpoints/observation/intervention/governance obligations with the action's declared obligations. Omitting request fields cannot weaken accepted requirements. Ordinary create_task creates an initially unprotected task within its grant; a later request cannot overwrite an existing protected task. The embedding host must route protected creations through the governed method. accepted_oversight exposes the retained policy to a scoped reader. Policy-revision advance preserves these obligations; no general policy-candidate activation or goal/budget editing API is implemented here.

## Exact decision binding and retained history

preview_approval checks the current task/proposal and returns ApprovalBinding: task_id, proposal_id, plan_revision, canonical payload_sha256, state_revision, policy_revision, exact task resource_scope, the union of accepted/declared checkpoints, and expires_at. G09 canonical task/proposal bytes bind effects and exclude only transport contexts. Accepted task obligations are checked separately through their immutable record/checkpoint union and current policy revision; they are not silently inserted into the existing wire format. At most64 checkpoint/approval references are accepted.

create_approval requires a current scoped verified HumanSession with ApproveAction. It recomputes the standard host SHA-256, checks every binding field, current material task/policy revisions and expiry, then retains an immutable decision with the verified principal and observed timestamp. Approval IDs are globally reserved EventId references used by the separate approval lookup; no execution event or effect observation is fabricated for that audit record. Incoming IDs must resolve in this runtime. Public snapshots cannot mutate the retained decision.

admit_with_approvals supplies record IDs, never authority from reference text. Every effect rechecks the binding, expiry, revocation and issuer delegation under the current policy. A plan's own observed mutations advance its leased live revision while its approval base remains the immutable admitted task/proposal; unrelated material/policy drift requires a new decision. Identical scoped queued/completed replay returns the existing execution before a new approval use, including after expiry. Replays perform no new effect; unauthorized access is still rejected. Changed payload/plan/state/scope cannot reuse an approval.

revoke_approval records the authorized verified principal/time without erasing the original decision. Revocation prevents future steps once recorded; prior applied effects/value/evidence remain. Expiry or revocation during a plan yields Failed with its actual error and partial results; it does not claim effective cancellation. Failed host time acquisition commits no revocation.

## Observation, intervention and command

ObserveEvents gates stream/observation/decision inspection independently of Read. Required intervention resolves at least one active scoped verified-human RequestCancellation enrollment under the accepted revision. A governance reference must resolve a registered, scoped task/revision decision issued by a verified-human GovernPolicy enrollment; a string alone fails. register_governance records that decision without activating a new policy. advance_policy accepts only a strictly greater task policy revision under the current scoped human GovernPolicy grant and retains the decision history; old execution/approval/grant bindings fail before another effect. A newly accepted grant must come from the trusted host. revoke_delegation is scoped, recorded and idempotent; it stops future use of that session, including its issued approvals, while retaining history. These commands govern this owned state; external release or arbitrary policy execution is not supplied.

## Receipt and effective cancellation

Admission reserves two additional control EventIds/slots when a matching verified-human cancellation capability is available. Both global and cumulative task event budgets include those slots before any effect. If a controller is enrolled only after admission, the old execution does not claim reserved interruption support and request_cancellation returns CAPABILITY_UNAVAILABLE. A required intervention obligation prevents such unsupported admission.

request_cancellation requires the current scoped verified-human RequestCancellation permission. It records CancellationRequested and a CancellationReceipt with the verified principal/observed request time, changes the snapshot to CancelRequested and returns the same receipt for duplicate requests. Receipt has no terminal result or effective_stop_evidence. It changes no task value. A clock/permission/instance failure leaves control state unchanged.

At its next FIFO worker turn, the runtime applies no further action, emits CancellationEffective with an actual owned-memory observation and produces Cancelled with result/effective-stop evidence. Reserved capacity makes that transition possible even when admission filled the declared event budget. Already confirmed effects remain; cancellation is not undo or compensation. A received cancellation still stops remaining work if delegation/policy changes afterward. Clock failure leaves CancelRequested pending, never inventing stop evidence. FIFO delay and cooperative stepping are explicit; this does not prove hard realtime, external or physical interruption.

A late request on Succeeded/Failed/Cancelled returns AlreadyTerminal containing the existing snapshot. It emits no replacement receipt and preserves terminal status, effects, errors, evidence and task value exactly. Request time and effective observation time are separate records; no latency/performance claim follows.

## Bounds and evidence

Approval, governance and policy-change registries are independently capped by Limits.executions; delegation/human enrollment is capped by Limits.sessions. Audit creation reserves one globally unique ID/event-budget slot plus a conservative16KiB resident-wire envelope before commit; immutable task oversight references are accounted with task admission. Revocation occupies a fixed retained field in its decision or bounded enrollment table. Execution cancellation uses its already reserved two slots. This is structural retained wire accounting, not measured allocator memory. There is no eviction, durable acknowledgement or restart recovery; journal/recovery remain G12/G13. Audit lookups and execution stream observations are separate surfaces.
