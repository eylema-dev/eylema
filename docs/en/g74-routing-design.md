## 2. Stable routing contract

An immutable registry revision contains at most 16 unique route entries. Each entry pins route ID/revision, intent (`retrieval`, `typed_skill`, `code`, `document`), source references/put digests, profile/schema versions, backend identity and required role/model bindings. Each entry has at most8 distinct source references and9 distinct role bindings; use existing bounded nonsecret ID types and reject duplicate/dangling references. Model bindings pin role, profile/revision, manifest/artifact/tokenizer/preprocessing fingerprints, context ceiling and parameter/resource declarations; unknown type or unsupported backend is explicit unavailable. Models are optional for deterministic routes. There is no family-name switch that equates popularity with support.

Only the sealed router owner together with the actual project owner may register entries against their original live ProjectStore. Sources must currently allow Execute, including ancestry; registration stores references/pins, not reusable permission receipts. Nonzero identities are structural pins, not authenticated publisher/model-quality evidence. Host-maintained accepted-profile/quality-policy revisions and validity intervals are explicit trusted configuration. Request-supplied strings cannot create an accepted model or quality floor. The registry is ephemeral; reopen requires fresh owner registration and enrollment, and invalidates old discovery/selection handles.

A request binds registry/policy revisions, project, explicit candidate IDs, task intent, local-only privacy requirement, context/response bounds, current capacity snapshot identity/revision and required quality profile. At most8 candidates are supplied. No free-form prompt classifier or hidden model call is introduced. The caller supplies typed intent and declared candidate assessments; a future accepted model adapter may produce assessments behind this same interface. Such assessments are untrusted proposals.

Comparable assessments use integer utility units 0–1000000 with one common scoring-profile revision and provenance reference. These units are neither calibrated probabilities nor verified confidence. Missing/mixed score profiles reject comparison. For this initial policy, require best score≥500000 and a margin≥100000 over the next eligible candidate; exact ties or smaller margins yield `Abstain`. With one eligible candidate, only the floor applies. Selection is exact integer comparison, with no learned/numerical kernel. Removing an ineligible route never authorizes a privacy fallback: every candidate must independently match the requested intent and explicit allowed set. Record excluded reasons without exposing unauthorized private catalog details.

Return one of `Selected`, `Abstain`, `Unavailable` or a typed validation/authority/budget error. Selection returns an opaque host-bound handle, not execution permission. `Unavailable` means no supported eligible handler; an empty candidate list or missing assessment is not a successful empty search. Changing registry, policy, task, selected arguments or source pins invalidates the handle.

## 3. Resource, context, quality and privacy admission

For each considered route, compute its declared resource result through the existing G80 estimator rather than accepting a caller's `fits` flag. Bind snapshot ID/revision/validity, resident model keys, parameter count, backend, context/state/workspace, auxiliary RAG/skill memory and declared overlap group. All required route invocations and currently declared concurrent occupants must appear; missing coverage is unknown. Preserve unified physical-pool identity and shared-resident deduplication. Unknown/stale evidence, changed keys, missing coefficients or an upper bound exceeding the declared available pool prevents selection. `EstimatedFit` remains planning-only, not measured physical capacity or permission. Actual execution retains its handler's independent resource admission.

Check source/profile/catalog/capacity/quality-policy validity against host-observed time. Request context plus declared response reserve must fit each selected profile with checked addition. Declared token counts are not authenticated tokenizer results. This slice does not infer tokens from bytes/words: a request requiring verified token counting returns unavailable until an accepted counting adapter is present. Byte-bounded retrieval/skill flows remain usable; token limits on G70 keep their existing unavailable result. Unsupported model-executing routes remain unavailable even with plausible metadata or an estimated fit.

Local-only requests cannot select external/provider routes or disclose project records. No automatic remote fallback, download, training, collection, export or ecosystem permission is granted. A quality-policy identifier denotes the host's declared accepted scope and floor; it is not a fresh quality measurement. General EN/TR relevance, specialist competence and model performance remain separate evaluations.

## 4. Catalog → describe → authorized call

Catalog returns only currently Execute-authorized entry summaries, with bounded IDs/revisions and available/unavailable classification. Explicitly requesting an unauthorized entry returns a uniform authority error before revealing existence, revision or backend details. Authorize all explicit requested references before private status/scoring; never return a partial private result after one reference fails. A catalog contains at most 16 entries and 8192 serialized bytes.

Describe loads only explicitly selected immutable references, at most 8 unique references and 32768 total source bytes. Current DataMetadata has no payload length. Add a narrow crate-private ProjectStore helper that first runs the existing Execute/session/ancestry authorization and then returns the stored payload length without copying or exposing bytes. Check those authorized lengths and request extents before reads/decoding; reserve the aggregate before any read. No public metadata/contract change is needed. Use G63 reads and canonical existing EYL validation, preserving kind/schema/revision/source digest. A skill must be an existing G75 package; model-dependent or other adapters remain unavailable. References are data, never instructions to enlarge authority. Stage at most 16384 serialized description bytes, including provenance, then recheck all sources/ancestors, sealed session and registry/policy TTL at one common final persisted trusted-time observation. Debug output contains counts/status only. No description body is cached in the selection handle.

Call consumes the selected handle plus the current explicit typed request. Recompute the request's canonical fingerprint using existing host SHA256, including selected route/profile/source pins, retrieval query or full ToolPlan/SkillLoop, context and resource snapshot. Recheck original live store/registry identity, current session/source/ancestry rights, revisions, TTL and budgets. A copied digest or another equal-looking store cannot substitute for the sealed binding. A described skill remains subject to unchanged ToolRegistry schema/operation validation, G75 source resolution, G10/G11 state/approval/intervention admission and G54 per-step checks. No unrestricted resolver/callback or bypass API is added.

Retrieval calls the actual G70 search with explicit source allowlist and unchanged representation/query bounds. It returns source-linked retrieval evidence or `NoMatch`; it does not synthesize an answer or prove source truth. Contradiction declarations prevent selection; undeclared contradictions cannot be automatically detected by this router. Skill calls return actual admission/execution identity and retain existing step/stop/report behavior. `Admitted` is not `Completed`; a completed skill substage is not whole-job completion. A selection/description is never an execution receipt. Use source controls at every actual effect and result handoff; already disclosed bytes or completed effects cannot be recalled.

Recheck final combined result references and validity at one common host time after staging. Cancellation/deadline or a final denial returns no partial new private result. Actual previously admitted effects retain their truthful existing state; never relabel them rolled back. No speculative retry, reselection after effects, nested skill execution or automatic fallback is included.

## 5. Finite bounds and failures

In addition to existing stricter handler limits: 16 registry entries,8 candidates,8 description references,32768 staged source bytes,16384 description bytes,65536 maximum canonical request/result bytes,64 MiB router-owned logical transient reservation,10000000 router work units and5 seconds cooperative router deadline per operation. Existing retrieval work/deadline/memory controls are separate required child ceilings and must fit the caller's total envelope; selecting a route does not reset either budget. Existing skill actions retain their own finite deadlines/cancellation and can outlive the router's synchronous admission operation.

Validate collection lengths, advertised/actual byte extents and checked aggregate reservations before copying/reading/decoding. Charge comparisons, visited bytes, hashing/serialization and per-entry work before that work, including staging and final sweeps; check stop/deadline at bounded intervals. No unmetered scan of oversized input. These are logical/cooperative bounds, not a process RSS limit or hard native-IO deadline. Caller-held stores/objects, allocator slack and OS buffers remain separate. Preparation/concrete plan must define exact child-control mapping and independent boundary fixtures; a missing mapping blocks implementation activation.

Typed failures distinguish invalid input, stale identity/revision, forbidden, unsupported capability, resource/context limit, cancellation, timeout and unusable source. Public authority errors do not reveal private absence/withdrawal details. Never collapse `NoMatch`, `Unavailable`, `Abstain`, admission and completed handler outcomes into one success flag. This slice adds no persisted router journal: restart invalidates transient handles without replaying effects. Existing task journals keep their accepted behavior.
