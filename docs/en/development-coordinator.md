# Development coordinator — G38

[Türkçe](../tr/development-coordinator.md). The owned `eylema-development` Rust library executes the development control state machine. It uses first-party contract identifiers, has no external package or unsafe code, and performs no provider, process, workspace or GitHub operation. G39–G43 supply those separately accepted hosts/adapters and real delivery evidence.

The trusted control host admits a bounded typed NeedSpec: repository/request/revision key, source issue, objective, acceptance scenarios, exact-file/directory scope, exclusions, targets, authority reference and finite call/repair/wall/usage limits. This is owned semantic state for NeedSpec 0.1; it adds no JSON parser or schema revision. Dependency policy remains first-party Rust and delivery is draft PR only. Strings are data. Issue text, a provider role or `authorization_ref` cannot grant permission.

`AuthorityResolver` is a trusted host interface. Its resolved `AcceptedTask` must equal the complete immutable NeedSpec and binds base commit, principal, policy and expiry. Every progress/reservation/readiness call rechecks that record; denial, expiry or a changed grant blocks progress. Host identity/policy verification and evidence provenance remain host responsibilities. These public Rust constructors do not authenticate a person or prove that supplied check/review observations ran. Contributor/provider code must not execute in this control process or call these evidence methods directly; G39 establishes actual isolation. A separately named context alone is not proof of independent review.

The flow is `received → spec_ready → planned → implementing → local_verification → independent_review → draft_pr → repository_checks → ready_for_maintainer`. Plans bind the accepted base and map every acceptance ID to named checks. Changes must fit lexical scope. Required local checks, separate-context review with no blocking findings, draft-PR observation and repository checks bind the exact current head. No missing, failed or stale required evidence advances its gate. A repair discards the old head/verification/review state, returns through implementation and consumes a repair allowance; a known PR identity is retained. A changed head needs fresh checks and review. Readiness grants no merge, publication, release or spending authority; the host must call `readiness` again when acting on it, supplying actual observed head and target-base commits. Either changing blocks readiness until a newly accepted task/reverification.

The bounded in-memory `Registry` retains one run per repository/request/revision: same-key receipt returns its existing state, counters and start time; conflicting content fails. It admits at most 128 runs and exposes no eviction/reset method. It does not persist across host restart or coordinate multiple hosts; durable retry/GitHub reconciliation follows in G39/G42. Registry admission does not itself authorize the task.

Before a provider effect, `reserve_call` charges one call and a positive conservative host-defined usage ceiling. Only one call can be in flight; task-scoped tickets reject mismatched/replayed completion. Failed/unknown calls retain the full reserved ceiling. Adapters must enforce that ceiling rather than treating a reservation as billing evidence. Usage units are not currency or measured tokens. Missing-input waits and repairs preserve all consumed budgets. Wall time continues during waits; host time must be monotonic, use the same epoch as grant expiry, and be polled while effects/waits run. A regression or exhausted ceiling cannot start another effect.

Cancellation without a pending effect enters `cancelled`. With a pending call it enters `cancel_requested`; only the host's matching completion acknowledgement enters `cancelled`. Budget exhaustion also retains any outstanding ticket until acknowledgement. An exhausted in-flight call still accepts a cancellation request and becomes cancelled on acknowledgement; cancelling an exhausted run with no pending call is an idempotent no-op. Completion cannot revive readiness. These states do not prove an OS process stopped, account for an external outcome, or undo earlier effects. The future process/provider host must stop actual work and preserve unknown outcomes.

Run behavioral regressions with `cargo test -p eylema-development --locked --offline`. Run `cargo run -p eylema-development --example coordinator-proof --locked --offline` for native execution of the state machine using explicitly synthetic host authority/check/review fixtures. It verifies denial and reaches the state awaiting a draft PR; it invokes no actual provider/reviewer/PR. Native tests/proof and selected library Wasm compilation remain distinct from G40–G43 real provider acceptance. This task needs no GPU, browser or model/training run.
