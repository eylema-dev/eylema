## Unicode contract and provenance

Choose **Unicode16.0.0** from existing reviewed CPython3.14 development tooling. The observed development interpreter is3.14.8, `unicodedata.unidata_version`16.0.0. Do not use Rust's moving character classification or silently regenerate with local Python3.15/Unicode17. Runtime uses our authored Rust algorithms and generated immutable data; Python is never called by the runtime. Derived Unicode data is an explicit separately attributed data input under [Unicode terms](https://www.unicode.org/license.txt), not a third-party engine or crate. Preserve the notice/provenance alongside generated data; first-party code remains Apache-2.0. No upstream implementation is copied.

## Byte encoding and prompt subset

Apply NFC, then reproduce the pinned pattern's ordered alternatives, isolated split behavior and byte-level transformation without prefix-space insertion. The256byte mapping is a validated bijection. BPE follows exact merge ranks, with deterministic left-to-right non-overlap handling and checked work; no unknown replacement or stochastic dropout. Decoder rejects unknown IDs and invalid/incomplete UTF8; valid declared added-token IDs decode to their literal spellings, never authority. No lossy replacement, implicit truncation or template substitution.

Initial prompt supports optional first system, then user and alternating assistant/user plain-text history, ending with user; at most8messages. Reproduce the exact no-tools, non-thinking pinned-template subset and generation prefix. No tool records, multimodal fields, arbitrary role names, reasoning-content fields or Jinja execution. Plain message/text input containing any of the26added-token spellings, before or after NFC, rejects before output; structural IDs are inserted only by typed formatter code. This intentional accepted subset prevents user content becoming control delimiters and does not claim unrestricted upstream text/template compatibility. Decoder output is data, not a role/action instruction.
