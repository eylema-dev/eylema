# Local journal — G12

The owned `eylema-journal` crate stores bounded canonical EYL values and detects torn, incompatible and corrupted records. Its production dependency is the owned contracts crate. Development consumers use the owned runtime and platform; there is no external Cargo dependency or copied journal engine. G13 owns semantic runtime restart recovery. Reading a typed contract does not restore a session, verified principal, approval, effect or execution authority.

## Format and bounds

The eight-byte header is `45594c4a01000000`: magic `EYLJ`, version 1 and three zero reserved bytes. A frame contains big-endian sequence u64 (starting at 1), payload length u32, previous digest (32 bytes), digest (32 bytes), then canonical EYL v1 payload. The initial previous digest is all zeros. Standard host SHA256 covers the journal header, sequence, length, previous digest and payload. This chain detects accidental corruption; it is not authentication against a writer who can recompute hashes. Unknown version/reserved bits or payload codec versions fail explicitly. Sequence, chain, digest, canonical payload and strict frame boundaries are checked before accepting records; malformed input is never automatically truncated, repaired or migrated.

Defaults are 4096 records, 1 MiB per payload and 64 MiB per file. Configurations must remain within 1–65536 records, 8–4194252 payload bytes and 8–1073741824 total bytes. Declared lengths and file/record limits are checked before payload allocation. The 52-byte hash envelope keeps SHA input within the platform's 4 MiB limit. The codec's depth/node/text/byte bounds also apply. Each exact read/write permits at most 4096 IO attempts including interruptions; exhaustion returns `TimedOut`. These are structural bounds, not allocator-memory or hard latency guarantees. Host filesystem operations can still block.

## Host ownership and acknowledgement

`NativeStorage` uses a trusted host-configured macOS path in an owner-controlled directory, creates fresh files with mode 0600, owns an exclusive nonblocking `File::try_lock` and exposes no cloned/raw file handle. A second cooperative writer receives `WouldBlock`; close/drop releases the lock. Existing empty files are truncated input, never silently initialized. Existing files are not permission-migrated. Host directory ownership and path selection are prerequisites; untrusted request paths and hostile same-user writers are outside this boundary. [Rust File documentation](https://doc.rust-lang.org/std/fs/struct.File.html) describes platform-dependent cooperative locking and synchronization.

The append encodes, hashes, checks bounds and checks current length before writing. A successful receipt follows complete write, flush, file `sync_all`, parent-directory `sync_all`, the owned macOS `F_FULLFSYNC` binding, and expected-length verification. There is no weaker fallback. The platform owns the narrow unsafe System binding; the journal forbids unsafe Rust and accepts a trusted host synchronization callback. The current SDK declares command 51 and the variadic `fcntl(int,int,...)` ABI. [Apple synchronization documentation](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fsync.2.html) explains the drive-cache boundary and full synchronization request.

After a write begins, failed write/flush/synchronization/post-write metadata returns `WriteUncertain`, supplies no receipt and poisons the writer. Unexpected length returns `ExternalChange` and also poisons it. Further reads/appends return `NeedsRecovery`; explicit close and inspected reopen are required. Preflight invalid payload, bounds, hash, metadata or seek failure writes nothing. A scan failure also poisons an existing writer. Metadata-only checks do not detect hostile same-size replacement before append; cooperative exclusive ownership is required. Reopening validates the complete chain rather than inferring previous acknowledgement. Fully written bytes may survive a failed synchronization: parsing them cannot retroactively produce the failed caller's receipt. Complete-frame truncation cannot establish whether omitted records were previously acknowledged without external trusted knowledge.

Errors contain bounded enums, offsets and IO kinds, not payloads or filesystem paths. The trusted `Storage` and `Sha256` providers must report truthful operations and standard SHA256; request data cannot replace those providers. Unsupported native platforms fail explicitly. Portable Wasm acceptance continues to select contracts/platform only; no browser journal storage is supplied.

They cover every cut inside header/frame, version/reserved/sequence/length/chain/digest/canonical corruption, short/zero/interrupted/disk-full writes, read/seek/metadata/flush and each injected synchronization stage, hash failure, bounds, uncertain complete bytes, poisoned writers, cooperative lock conflict, native mode 0600, empty-file rejection and actual non-file full-sync failure.
